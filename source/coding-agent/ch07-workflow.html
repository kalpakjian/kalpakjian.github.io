里程碑、Ralph 迴圈與常見陷阱

不要一次做完。六個里程碑的順序本身就是護欄——先讓單一 agent 跑得穩，再談自動化。

這一章把前面的零件收束成一條可以照著走的路徑，並列出七個最常見的坑。

本章目錄

  1. 漸進式里程碑：不要一次做完
  2. 內層 agent vs 外層 Ralph 迴圈
  3. 常見陷阱
SECTION 01

漸進式里程碑：不要一次做完

階段目標驗收標準
M1唯讀 agent：list_files / grep / read_file能正確回答「這個 bug 在哪個檔哪一行」
M2加上 edit_file + git_diff能改一個函式且 diff 乾淨
M3加上 run_shell + 測試驗證迴路測試紅燈能自行修正到綠燈
M4Context 壓縮 + todo 外顯化連續 20 步不爆 context
M5護欄：路徑白名單、黑名單、dry-run、批准點嘗試 ../ 與 rm -rf 被正確攔截
M6外層 Ralph loop：規格檔 + 每輪單一任務 + 進度檔無人干預下完成一個小型規格
鐵則

M5 沒做完就不要進 M6。這是絕大多數人踩的坑——先讓它自動跑，出事後才想補護欄，順序完全相反。

SECTION 02

內層 agent vs 外層 Ralph 迴圈

這兩個名詞常被混用，但職責完全不同：

內層 agent外層 Ralph 迴圈
單位一個任務內的一步一整個任務／一輪迭代
Context累積當前工作狀態每輪清空重建
記憶對話歷史git log + 進度檔 + 規格檔
終止條件測試通過規格的所有驗收條件通過
誰負責模型你（規格設計者）

外層迴圈本質上就是：

while not spec_satisfied():
    spawn(agent, next_smallest_task)
    verify()      # 測試 / lint / type check
    commit()      # 讓下一輪能從 git 讀到自己的成果

所以「Ralph 不是框架，而是把工程師的角色從逐行寫程式，搬到規格設計與驗證」這個說法，在技術上是站得住的。它把工程師的職責重新排序成四件事：

  1. 寫清楚規格與驗收條件
  2. 設計可自動驗證的測試
  3. 控制 agent 的執行範圍與風險
  4. 審查、整合並修正產出
SECTION 03

常見陷阱

  1. 一開始就想做 multi-agent 或自主規劃 → 先讓單一 agent 跑得穩。（對應 M1～M3）
  2. 沒有測試就讓它自動跑 → 你得到的不是生產力，是高產能的破壞者。（見第 3 章）
  3. 工具輸出直接灌進 context → 兩輪就爆掉，模型注意力也被稀釋。（見第 2 章的三個鐵則）
  4. 用整檔覆寫代替精準 patch → 每次修改都產生巨大 diff，無法 review、無法回滾。（見第 2 章的 edit_file 設計）
  5. 沒有步數與 token 上限 → 一個迴圈燒掉一整天的額度。（見第 3 章的三重硬上限）
  6. 沒有 git 快照 → 失敗時無法恢復，只能手動收拾。（見第 3 章的動工前快照）
  7. 把「模型說完成」當成完成 → 唯一的完成定義是驗證器綠燈。（見第 1 章的零件 6、第 6 章的沉默失敗）
第 7 點在實測裡真的發生了

第 6 章的「差 121 tokens 的沉默失敗」就是這個陷阱的具體版本：Pi 回傳空輸出、exit code 0，看起來像「跑完了」，實際上是「從來沒開始」。當你的驗證器是 exit code，而 exit code 說謊時，你需要的是事件串流，不是更樂觀的假設。
