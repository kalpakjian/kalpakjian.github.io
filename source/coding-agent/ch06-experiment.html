實測 01

預設工具真的是四個

從 Pi 實際送出的 system prompt 直接讀出來：

<tools>
- read: Read file contents
- bash: Execute bash commands (ls, grep, find, etc.)
- edit: Make precise file edits with exact text replacement, including multiple disjoint edits in one call
- write: Create or overwrite files
</tools>

--help 另外列出了 powershell、grep、find、ls，但都標示 off by default。所以第 5 章那句「約四個原子工具」是準確的——而且這四個正好就是第 3 章那份骨架的四個工具。

實測 02

「system prompt 極小」只對一半

把 Pi 的 system prompt 依區段拆開量測：

區段字元~tokens佔比
preamble169420.6%
tools339841.1%
rules8392092.8%
docs1,3793444.6%
project_context（AGENTS.md ×2）4921962.6%
skills25,2766,54088.6%
cwd3480.1%
  • 核心（preamble + tools + rules + docs + cwd）= 2,760 字元 ≈ 487 tokens。「極小」對核心而言完全成立。
  • 但 skills 索引獨佔 88.6%。它來自 ~/.agents/skills/ 底下約 30 個 Azure／AI skill，Pi 會把每個的 name + description + location 全部注入。
「小」最容易被誤解的地方

Pi 的核心確實極小，但 harness 的實際 prompt 成本 = 核心 + 你機器上所有被自動發現的東西。同一個 Pi，在不同人的機器上，prompt 可能差一個量級。context 預算是「你環境的函數」，不是「產品的常數」。

實測 03

差 121 tokens 的沉默失敗

Pi 預設接的是 8K context 的模型。實際送出的 prompt 是 8,313 tokens——比 8,192 多 121：

400 exceed_context_size_error
n_prompt_tokens: 8313, n_ctx: 8192

Pi 的錯誤處理其實很正確：stopReason: "error"、willRetry: false、durationMs: 214，並附加一個 context_edit 事件後才 agent_settled。

但在 -p（非互動）模式下，使用者只看到「空輸出 + exit code 0」。

沉默失敗比錯誤訊息更危險

我第一時間誤判成「Pi 不支援非互動模式」，因為它 1 秒內就結束、且零輸出。真相是它在快速失敗。要看到原因，必須用 --mode json 去讀事件串流。

這和第 7 章的陷阱是同一類：「程式結束了」不等於「任務完成了」。差別只在這裡的驗證器是 exit code，而 exit code 說謊了。

修法是把它升到 32K（載入佔 18.4 GB VRAM，4090 綽綽有餘）：

Modelfile 
FROM qwen3.8-27b-uncensored:latest
PARAMETER num_ctx 32768

三個模型都解掉了任務，但軌跡與成本差距很大：

  • 12B：先跑測試拿到紅字，再回頭讀檔、一次改對。工具呼叫最少（4 次），但單回合輸出比 27B 大。

這正是第 4 章那句話的實測版本

harness 完整不保證等於強 agent。harness 一樣、規則一樣、任務一樣、AGENTS.md 一樣，差別只在那顆模型——而差距具體表現在三件事上：先調查還是先動手、一次改對還是來回兩次、輸出 438 還是 5,378 tokens。

實測 05

thinking 等級的影響

固定 27B + 32K，只改 --thinking：

thinking工具序列工具呼叫數輸出 tokens牆鐘時間
offread → read → bash → edit → read → bash660510.1 s
mediumbash → read → read → edit → read → bash65128.2 s
highbash → read → edit → bash44908.2 s

趨勢是：thinking 越高，工具呼叫越少、輸出越省、軌跡越直接。high 只用了 4 次工具呼叫就完成，而 off 來回 6 次。

但要誠實說：每一格只有一組樣本，雜訊不小。同一個 thinking 等級重跑，軌跡就會變——例如 medium 第一次是 read → read → bash → edit → bash，第二次變成 bash → read → read → edit → read → bash。所以這張表該讀成「趨勢」，不是「定論」。

比 thinking 更大的變數：prompt cache

同一組設定（27B / 32K / thinking=off）跑兩次：冷快取 29.5 秒，暖快取 10.1 秒——差 3 倍，而且與模型、thinking 都無關。

也就是說，當你在本地量測 agent 的效能時，第一個該控制的變數是快取狀態，不是模型參數。這也是為什麼後面那張總表的「牆鐘時間」欄要配著看。

實測 06

把 prompt 削掉，8K 模型就活了

回到實測三那個撞牆的 8K 模型。既然問題出在 prompt 有 8,313 tokens，那就把 prompt 削掉——加上 --no-skills：

8K + skills8K + --no-skills
system prompt~7,426（Ollama 實測 8,313）~886
首回合 input被 400 拒絕1,852
上下文峰值—2,762
工具序列—bash → read → read → edit → bash
輸出 tokens—451
結果❌ 空輸出 + exit 0✅ 4 passed

同一個模型、同一份 harness、同一個任務，只差一個 --no-skills，就從「完全不動」變成「順利完成」。

而且注意它的輸出 tokens 是 451——和 27B + 32K 的 438 幾乎一樣。上下文峰值 2,762 更只有原本的 3.3 分之一。

這是第 2 章那三個鐵則的極端版

第 2 章說 context 管理是真正的難點，三個鐵則是「截斷輸出、grep 定位、摘要舊輪次」。這個實驗把同一件事推到極致：當 harness 的固定開銷就吃掉整個視窗時，你連第一句話都說不出口。

而且解法不一定要換更大的模型——先問「這些 token 是誰塞進來的」，通常比換模型便宜得多。

實測 07

三個意外驗證

1. 專案規則真的生效——而且 11 次全中。掃過所有執行的原始事件串流：沒有任何一次的 edit／write 動到 test_calc.py，git diff 也顯示只有 calc.py 被改。三個模型家族、五種設定、11 次執行，AGENTS.md 寫的「只修改 calc.py」100% 被遵守。第 3 章講的護欄不一定要寫在程式碼裡，寫在專案規則檔也有效。

2. edit 的唯一匹配設計是對的。27B 送出的參數：

edit {"path": "calc.py", "edits": [{
  "oldText": "    # BUG: off-by-one, should be total / len(numbers)\n    return total / len(numbers) + 1",
  "newText": "    return total / len(numbers)" }]}

oldText 精準涵蓋 bug 行加上方的註解行，一次命中、零歧義。這正是第 2 章描述的「Claude Code 風格精準 patch」——不是把整檔重寫，而是用最小且唯一的片段定位。

3. Prompt caching 讓 agent 迴圈變便宜。27B 那次五個回合累計 cacheRead 43,165 tokens，但真正新增的 input 只有 809 tokens。每一回合只重新計算約 100–280 個新 token，這是 7.9 秒跑完的主因。

對本地推論的意義

agent 迴圈的成本瓶頸不是「context 有多大」，而是「每回合新增多少」。這也是為什麼第 2 章那三個鐵則（截斷輸出、grep 定位、摘要舊輪次）值得認真做——它們削的正是每回合的新增量。

附錄

Pi 的事件格式：自建 harness 的參考

--mode json 輸出的是事件串流，結構乾淨到可以直接照抄：

session → agent_start → turn_start
  → message_start / message_update / message_end / turn_end   （每回合重複）
→ agent_end → agent_settled
+ entry_appended（含 context_edit，即壓縮事件）

注意 context_edit 是一個獨立事件，不是藏在訊息裡——這讓「agent 什麼時候壓縮了 context」變成可觀測的事實，而不是黑箱。要自建 harness 的話，這個事件設計值得直接借用。

一句話

Pi 給了你一個小到能讀完的核心，但沒有給你小到能忽略的環境。能不能跑起來，取決於你有沒有先量過自己的 context 預算。
