一個 coding agent 只有六個零件

不管是一百行的研究原型，還是百萬行的產品，拆開來都是同樣六個零件。

起點是 Geoffrey Huntley〈Replaced〉那句話：「2026 年的資深工程師應該能重建 Claude Code 這類最基本的 agent。」

本章目錄

  1. 先把那句話拆開：哪部分合理，哪部分過頭
  2. 一個 coding agent 只有六個零件
  3. 資料流：一句話講完
SECTION 01

先把那句話拆開：哪部分合理，哪部分過頭

Huntley 的原意並不是「每個人都要複製 Anthropic 的產品」。他指出的是你應該懂 agent 的基本構成：

  • 讀取專案檔案與程式碼
  • 呼叫 shell、測試、git 等工具
  • 維持任務上下文
  • 根據錯誤結果迭代修正
  • 在適當時機停下來交給人審查

換言之，重點是能設計與駕馭工作迴路，而不是只會在 IDE 裡按「Accept suggestion」。至於「做不出 Claude Code 就不算資深」這種講法，當成警號與練習目標可以，當成資格判定就過頭了：

說法合理程度判斷
工程師應理解 context window、tokenization、工具呼叫與 agent 迴圈高這是現代 AI 工程的基本素養
應該有可展示的 AI 實作專案高比只會聊天式使用 AI 更有說服力
應能自己建立小型 coding agent中高對後端、平台、自動化、AI 工具工程師特別有價值
做不出 Claude Code 就不是資深工程師低到中過度絕對；資深價值還包括系統設計、維運、安全、領域知識與團隊協作
用 AI 兩週完成過去 50 萬的專案需保留可能發生，但高度依賴專案類型、既有程式碼、測試與人類監督

Tobi Lütke 的立場則更接近管理層面的要求：AI 不再只是個人效率工具，而是影響招聘、資源分配與績效評估的工作方式。但這也不等於「所有工程師都必須造一個 Claude Code」，Shopify 的要求更接近「必須主動、熟練地將 AI 納入日常工作」。

本專題的立場

「資深工程師要能重建 Claude Code」適合當成練習目標，不適合當成資格判定。真正會被淘汰的不是「沒有自己寫 Claude Code」的人，而是仍然只用 AI 複製貼上、無法設計驗證、也不願承擔工程責任的人。

SECTION 02

一個 coding agent 只有六個零件

不管是一百行的研究原型，還是百萬行的產品，拆開來都是同樣六個零件。前五個是內層 agent（Claude Code 本體），第六個加上「規格檔 + 每輪單一任務」就是外層 Ralph 迴圈。

這不是紙上分類。市面上已經有把六個零件全部做出來的成品——例如 Cline CLI；也有反過來只保留最小核心的 Pi。第 4～6 章會拿這兩個開源 harness 逐一對照，並實際把其中一個接上本地模型跑一次，看同一組零件在兩種相反的設計哲學下長成什麼樣子。

#零件作用對應文章中的說法
1模型（policy）決策：下一步做什麼可替換，本地或 API 皆可
2工具（action space）它能對世界做什麼讀檔、shell、測試、git
3迴圈（control loop）決策 → 執行 → 觀察 → 再決策「設計與駕馭工作迴路」
4Context 管理器決定模型每一輪看到什麼維持任務上下文
5護欄（guardrails）沙箱、白名單、步數上限、人工批准「適當時機停下來交給人」
6驗證器（verifier）測試／lint／type check／git diff「根據錯誤結果迭代修正」
最容易被忽略的一點

第 6 個零件不是選配。「完成」的定義必須是可驗證的——測試綠燈、型別檢查通過、diff 符合預期——而不是模型說「我做完了」。這是整套設計的靈魂，也是業餘作品與工程級 harness 的分界線。

SECTION 03

資料流：一句話講完

目標 ──▶ [ system prompt + 工具 schema + 當前狀態 ] ──▶ LLM
          ▲                                              │
          │                                        tool_call
          │                                              ▼
      結果截斷後回饋 ◀── 執行工具（讀檔／改檔／跑測試／git）
          │
          └── 重複，直到：模型宣告完成 ／ 驗證通過 ／ 超過步數 ／ 需要人工批准

整個 agent 就是這個 while 迴圈。所有複雜度都藏在「括號裡那三件事」：餵什麼給模型、允許它做什麼、怎麼判斷它做對了。

接下來兩章就是把這三件事逐一展開：第 2 章先講「餵什麼」（工具與 context），第 3 章再講「允許它做什麼」與「怎麼判斷它做對了」（護欄與驗證迴路），最後把它們寫成一支 90 行的骨架。
