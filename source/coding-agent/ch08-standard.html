一個比較健康的資深標準

如果要把 Huntley 的說法改寫成一句可以真正拿來自我要求的話，我會這樣寫：

一位 2026 年的資深工程師，應該能安全地將 AI agent 整合進真實工程流程，並能判斷何時該信任它、何時必須介入。

結語 01

具體能力包括

  • 能把模糊需求轉成可驗證的規格
  • 能設計測試、型別檢查與 CI，作為 agent 的煞車系統
  • 能評估不同模型、harness 與 token 成本
  • 能審查 AI 產生的架構與安全風險
  • 能教團隊建立可重複的 AI 工作流
結語 02

回到實作層面

做一個 coding agent，就是做一個「有嚴格工具介面、有預算限制的 context 管理器，外面套一層可驗證的迴圈」。把 context 預算、工具權限、驗證與回滾做對，你就已經做出 Claude Code 的核心骨架，也才真的符合那個「能設計與駕馭工作迴路」的標準。

而 Cline CLI 與 Pi 正好從兩個方向證明了同一件事：Cline 把六個零件都做到了生產級，Pi 把核心拆到只剩四個原子工具——所以你不需要從零造一個；但如果你不清楚那六個零件在做什麼，你既看不懂 Cline 的黑箱，也配不出 Pi 的護欄。harness 可以下載，判斷力不行。

這也是為什麼第 5 章要把 Pi 的六步練法接回本專題結構：它給的不是一條新路，而是同一條路的三層視角——怎麼用 agent、怎麼擴展 agent、怎麼從零重建 agent。三層都走過一次，你才算真的把 harness 變成自己的能力，而不是把某個產品的操作手冊背下來。

第 6 章的實測則補上最後一塊：這些都是可以被量測的。8,313 tokens 的 prompt、7.9 秒的迴圈、12.3 倍的輸出差距——當你能報出這些數字，你就不再是「感覺這個 agent 還行」的使用者，而是能診斷它的人。
