工具設計與 Context 管理

工具是 agent 唯一能改變世界的手段；而 context 不是「把東西都塞進去」，是每一輪重新組裝。

六個零件裡的零件 2 與零件 4——這兩格決定 agent 能做什麼，以及它每一輪「看得到什麼」。

本章目錄

  1. 工具設計：不要一開始就給 30 個工具
  2. Context 管理：真正的難點
SECTION 01

工具設計：不要一開始就給 30 個工具

工具是 agent 的 action space，也是它唯一能改變世界的手段。最小可用集如下：

工具關鍵設計點
read_file(path, start, end)帶行號區間，不要整檔塞進 context
list_files(glob)先讓它知道專案長什麼樣
grep(pattern, glob)定位比全讀便宜 100 倍
edit_file(path, old, new)old 必須唯一匹配，否則回報錯誤讓它重試
write_file(path, content)僅用於建立新檔
run_shell(cmd, timeout)黑名單 + 逾時 + 輸出截斷
run_tests()包好的測試指令，agent 不必自己猜
git_status / git_diff讓 agent 看到自己改了什麼
todo_write把計畫外顯化，防止它亂飄

edit_file 的「old 必須唯一匹配」是 Claude Code 風格精準 patch 的核心。若同一段文字出現兩次，工具應該拒絕執行並回報出現次數，而不是猜一個位置改下去——這樣才不會產生無法 review 的巨大 diff。

每一個工具都要有：JSON schema、權限等級、逾時、輸出上限、人類可讀的錯誤訊息。錯誤訊息寫得好，等於免費提升 agent 的成功率。

對照組預告

第 5 章的 Pi 只有四個原子工具（read／bash／edit／write），而第 4 章的 Cline CLI 把工具層做到包含 MCP servers 與 lifecycle hooks。先記住這一格的形狀，後面兩張表會回來對照它。

SECTION 02

Context 管理：真正的難點

Context 不是「把東西都塞進去」，而是每一輪重新組裝：

[ system  ]  角色 + 工具使用規則 + 安全紅線
[ project ]  專案規則檔（類 CLAUDE.md）：怎麼跑測試、禁止改哪些目錄
[ task    ]  本輪唯一任務 + 驗收條件            ← 每輪重新注入（乾淨 context）
[ state   ]  當前 todo + 最近一次錯誤 + git diff
[ history ]  舊輪次壓縮成摘要，工具輸出只留頭尾

三個鐵則：

  1. 工具輸出一定要截斷——保留開頭與結尾，中間省略。一次 npm test 的完整輸出就足以吃掉半個視窗。
  2. 檔案用 grep 定位 + 區間讀取，不要整份讀進來。
  3. 超過預算就摘要舊輪次，但「目標與驗收條件」永遠不能被摘要掉。
這就是 Ralph 所謂的「乾淨 context」

Ralph 迴圈常被形容成一種神秘框架，但它技術上只是在做一件事：每一輪都把 agent 的 context 清空重建，只留下目標、規格與驗收條件，讓它從 git 紀錄、進度檔與測試結果重新認識自己的處境。這不是魔法，是 context 管理策略。

這三個鐵則會一路跟著你

它們不是本章的裝飾，而是後面幾章的伏筆：

  • 第 4 章：連生產級的 Cline CLI，在「長任務記憶與 context 管理」這一格都還只做到「中等」——這三個鐵則就是這個難題的最小解。
  • 第 5 章：Pi 的 Code Mode 是同一件事的更激進版本——與其把 200 行 grep 結果塞進 context 讓模型自己讀，不如讓模型寫一段程式去讀，只回傳結論。
  • 第 6 章：實測六會用一組「削掉 prompt」的對照，把這件事推到極致——當 harness 的固定開銷就吃掉整個視窗時，你連第一句話都說不出口。
